## 1. Scale From Zero to Millions of Users - Part 1

由於第一章的內容較多，預計將會分成三個部分進行講解。首先筆者會開始探討如何從零開始設計一個為百萬用戶服務的系統，並針對網站流量設定負載平衡器等相關的系統設定。

### 一、設立單純的伺服器

一開始最簡單的服務通常只會從一臺伺服器開始，其流程大概如下：

![簡單伺服器架構](/blog/sd-simple-server.png)

1. 用戶在瀏覽器輸入網址（如 `www.example.com`），瀏覽器向 DNS 伺服器詢問「這個網址對應哪個 IP？」
2. DNS 伺服器回傳 IP 位址（如 `15.125.23.214`）給用戶端，之後的通訊就直接用 IP。
3. 用戶端透過取得的 IP 向 Web 伺服器發送 HTTP 請求，索取網頁內容。
4. Web 伺服器將組合好的 HTML / CSS / JS 回傳給用戶端瀏覽畫面。

上述這樣只能算是最簡單的服務，用於讀取靜態網頁或是回傳 API 所提供的 JSON 檔案。
若是有大量資料需要存取的話，就沒辦法獲取資料了。因此，我們需要透過**資料庫**來讓伺服器回傳我們所儲存的各項資料。

### 資料庫

當用戶增加後，要把 Web 層和 DB 層**分開到不同伺服器**，這樣兩層才能各自獨立擴張，可以分為以下兩種：

- **Web/Mobile Traffic**：減緩網路流量，避免伺服器無法負荷流量暴增
- **Data**：用於儲存數據的資料庫

1. 用戶在瀏覽器輸入網址（如 `www.example.com`），瀏覽器向 DNS 伺服器詢問「這個網址對應哪個 IP？」
2. DNS 伺服器回傳 IP 位址（如 `15.125.23.214`）給用戶端，之後的通訊就直接用 IP。
3. 用戶端透過取得的 IP 向 Web 伺服器發送 HTTP 請求，索取網頁內容。
4. 讀取/寫入/更新 資料庫。
5. 資料庫回傳所需要的資料。
6. Web 伺服器將需要的資料，包含組合好的網站畫面回傳給用戶端瀏覽畫面。

![伺服器與資料庫架構](/blog/sd-server-with-db.png)

至於資料庫也有兩種，分別為關聯性資料庫（Relational database / SQL）及非關聯性資料庫（Non-Relational database / NoSQL），使用者可以依據自己需要的服務使用合適的資料庫。

- **SQL**：以 Tables & Rows 儲存結構化資料，支援透過 SQL 對不同資料表執行 JOIN 操作。常見的有 MySQL、PostgreSQL、Oracle 等。

- **NoSQL**：分為四種類型——key-value stores、graph stores、column stores、document stores，通常不支援 JOIN。當有以下需求時，NoSQL 會是更好的選擇：
    - 需要超低延遲（super-low latency）
    - 資料是**非結構化的，或彼此之間沒有關聯性**
    - 只需要對資料做序列化 / 反序列化（如 JSON、XML、YAML）
    - 需要儲存海量資料

### 垂直擴張 & 水平擴張

在擴張系統服務的時候有兩種選擇，分別為**垂直擴張（Vertical scaling）以及水平擴張（Horizontal scaling）**。簡單來說，前者是將電腦的各項功能變得更強大，後者是連結更多臺的電腦增加效能。

在系統設計中，水平擴張通常會是更常見的選擇，其原因如下：

- 垂直擴張所能擴張的強度終究有限。
- 若是伺服器離線，整個服務都會直接停擺。
- 垂直擴張成本較高。

另一方面，雖然水平擴張不太會遇到上述的兩項問題，但當多個用戶想要同時存取服務時，有可能會造成伺服器過載。在這個情況下，就需要**負載平衡器**（Load balancer）來幫助網站服務不會中斷。

### 負載平衡器

負載平衡器是一種網路流量分配技術，能夠將使用者的請求平均分配到多台伺服器上。在用戶連結到伺服器之前，先連接到負載平衡器，將網路流量平均分散到各台伺服器。

- 在 Server 1 掛掉時流量自動轉到 Server 2，
- 流量暴增時只要加入新伺服器，Load Balancer 就會自動分流。

為了避免內部系統直接暴露於公開網際網路，負載平衡器會透過私有 IP 與各個伺服器進行連結。

### 資料庫複製

在資料庫管理中，通常會遇到需要將資料庫的資料進行複製或是分割的情況，若是每個資料庫都擁有相同的權限，可以複製或是切割個別資料庫的儲存資料，就有可能會發生資料缺失或是無法存取的狀態。為了提升讀取效能與可用性，需要一種機制來管理資料的複製與同步，因此引入了主從式架構。

此時，有一種主流的資料庫複製方式，也就是**主從式架構設定**（Master/Slave Relationship），能幫助系統設計者解決這個問題。

- **Master 資料庫**：伺服器要寫入資料的話，都會寫入到 Master 資料庫中，並且由 Master 資料庫將資料副本複製到 Slave 資料庫中
- **Slave 資料庫**：無法寫入新資料，伺服器要讀取資料的話，就會從 Slave 資料庫讀取。

將資料庫進行複製有幾個好處：

1. **提升效能**：多個 Slave 資料庫進行讀取時能分散流量，能平行處理多項佇列要求。
2. **可靠性提升**：若是有資料庫損毀的話可以從其他資料庫獲取資料。
3. **可用性提高**：網站在資料庫離線時一樣可以存取資料。

此外，當 Master 資料庫或是 Slave 資料庫離線時，其架構能隨時進行調整：

- **Slave 資料庫下線**：新的 Slave 資料庫可以馬上進行取代。
- **Master 資料庫下線**：其中一個 Slave 資料庫會被提拔到 Master 資料庫的地位，由它負責原本的 Master 資料庫的工作。
